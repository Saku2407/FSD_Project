Introduction

Why built-in validators are not enough

Django forms check the basics for you: a CharField can enforce max_length, an EmailField checks the email format, and an IntegerField rejects text. These built-in checks are useful, but real applications need rules that Django cannot guess:

  • A username may only contain letters, digits and underscores, and must not be a reserved word such as admin.
  • A user must be 18 or older, which is a business rule, not a data type.
  • The password and confirm password fields must match, so one field's validity depends on another.
  • A password must not contain the username.

The first three examples need your own logic. Django lets you add it by overriding methods on the form class.

How clean() works

When you call form.is_valid(), Django runs validation in three layers, always in this order:

  1. Built-in field validation. Each field converts and checks its own input (required, valid email, valid integer).
  2. Field-level hooks: clean_<fieldname>(). One method per field, used for rules about that single value.
  3. Form-level hook: clean(). Runs last, once all fields are processed. Use it for rules that compare several fields.
MethodScopeTypical useError appears
clean_username() One field Length, allowed characters, reserved names Under that field
clean_age() One field Minimum age of 18 Under that field
clean() Whole form Password match, password vs username Under a chosen field, or at the top of the form
Key idea: if a rule involves one field, use clean_<fieldname>(). If it involves two or more fields, use clean().

Models change over time

After the first migration, the database holds real data. Changing the model now means changing a table that already contains rows, so Django records each change as a new migration that depends on the previous one. The migrations form a chain:

0001_initial→ 0002_book_published→ 0003_...

Operations Django generates

You change...OperationEffect on the table
Add a fieldAddFieldNew column; existing rows get the default (or NULL).
Remove a fieldRemoveFieldColumn is dropped. Its data is lost.
Rename a fieldRenameFieldColumn is renamed; data is kept.
Change a field's type or optionsAlterFieldColumn definition changes; data is converted if possible.
Add / remove / rename a modelCreateModel, DeleteModel, RenameModelTable is created, dropped or renamed.

Some databases, SQLite included, cannot perform every change with a simple ALTER TABLE. In those cases Django may rebuild the table behind the scenes.

Adding a field to a table that has rows

Existing rows need some value in a new column. If the new field is not nullable and has no default, makemigrations stops and asks you to choose:

  1. give a one-off default that is used only to fill the existing rows, or
  2. quit and set a permanent default=... (or null=True) in models.py.

Renames and the "Was it renamed?" prompt

Django only sees the old and the new model. If one field disappears and another of the same type appears, it asks: Was book.pages renamed to book.page_count?

  • Answer y: it writes a RenameField, so the data is kept.
  • Answer N: it writes RemoveField and AddField, so the old column's data is dropped.

Going backward

Most operations can be reversed (a RunPython step can be too, if you supply a reverse function). Giving migrate a target moves the database to that point, in either direction:

python manage.py migrate library 0001     # unapply everything after 0001
python manage.py migrate library          # apply everything again

Reversing a migration does not bring back data that its forward step destroyed. For example, if 0003 removed the pages column, unapplying it re-creates the column, but it is empty.

Data migrations and other tools

  • RunPython runs your own Python function inside a migration, which is the usual way to copy or transform existing data.
  • makemigrations --empty app creates a blank migration for you to fill in.
  • Long chains can be combined with squashmigrations.
  • If two developers create migrations from the same parent, makemigrations --merge can reconcile them.
